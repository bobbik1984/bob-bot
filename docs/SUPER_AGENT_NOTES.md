# Super-agent 设计研究笔记

> **来源**：DeepSeek 产品团队 2026-10-31 的《Super-agent Design Exploration》（经 [ChainCatcher 转载](https://www.chaincatcher.com/en/article/2300676)阅读，未读原文）。本文只记录对 BobBot 有用的结论，不是施工计划。

## 核心思路

单个 ReAct 循环难以同时做到持续运行、高效、主动和持久，因此拆成两层：

- **Router**：常驻的全局层，接收所有用户输入、分派任务、回复用户，自身不执行任务，可使用更轻的模型。
- **Worker**：上下文隔离的任务会话，带完整工具，只向 Router 汇报，不直接面对用户。

这与 BobBot 的 Resident Clerk + Native ReAct Worker 基本一致，说明双层方向是对的。

## 值得借鉴（按优先级）

| 想法 | 对 BobBot 的用法 | 建议阶段 |
| :--- | :--- | :--- |
| 程序规则优先过滤 | 收到渠道消息或定时事件时，先用白名单和规则判断，能不调用模型就不调用，直接节省月度预算 | BB3 |
| Thread 订阅直通 | 同一任务的后续消息直接进入对应 Worker，不经过 Router；原文实验中去掉直通后 Router 决策增加约 30%，且完成时间没有改善 | BB2 |
| 事件批处理 | 一次推理期间到达的多条消息合并到下一次调用 | BB2 |
| Inline & Spill | 上下文只放 ID 和摘要，其余按需读取，适合网页快照与历史任务 | BB2 |
| 按渠道限制回复长度 | IM 渠道用短回复（原文验证过 100 词上限），网页端用完整卡片 | BB3 |
| Watchdog | 定时检查 Worker 是否真有进展，发现循环就停止，避免空耗预算 | BB2 |
| 后台预先起草 | 提前准备好草稿，审批通过才发出，适合白领日常事务 | BB3 之后 |

## 暂不采用

- Router 水平分片、多层过滤、Worker 之间直接通信：单用户单 VPS 用不上。
- 跨设备边缘守护进程：BobBot 明确只管一台 VPS。
- 数月尺度的长期记忆：原文也列为未解决问题，先用记忆胶囊。

## 原文未解决、BobBot 也要注意的问题

- 凭据如何可用但不进入模型上下文。BobBot 通过人工接管登录、Cookie 留在浏览器里来规避。
- 原文的实验规模小且是合成任务，数字只能作参考。

## 官方原型：`deepseek-ai/dsh-superagent-prototype`（MIT）

这是基于 DSH 的研究原型，面向「单个 GitHub 仓库的主动编码 Agent」，可选接入飞书。官方说明它不是正式产品，也与文章中的实现不完全相同。

**结论：不直接采用，只借鉴。** 它依赖 Shell、GitHub CLI 和代码工作流，而 BobBot 面向白领、并已移除 Shell。以下内容值得借鉴：

| 想法 | 对 BobBot 的用法 |
| :--- | :--- |
| 核心原则「占用尽量少的人类注意力」 | 作为产品原则：确认一次，安静执行，只在有结果或需要决定时说话 |
| Source / Trigger / Thread / Channel 模型 | 作为 `ChannelAdapter` 的设计基础，Telegram、Lark 等都是一种 Source |
| 飞书 Source（`src/sources/`） | 接入 Lark 时的实现参考 |
| 权限由宿主程序强制执行，消息内容不能改变权限 | 渠道绑定用户与审批都放在服务端 |
| 主动任务先「只记录将要做什么」 | Routine 的试运行模式 |
| Outbox 回执，同一 Trigger 不重复执行 | 渠道收发与定时任务的防重复 |
| 一次只问一个具体问题 | 审批卡与接管卡的文案规范 |

## 当前原型的取舍

测试原型只有一个 DSH 会话，由它直接处理对话和工具调用，还没有拆分 Router 与 Worker。待单会话跑通真实任务后，再按上表引入。
